# AI Audit — Nukkia

A walk through the app's user journey, stage by stage, naming every point
where AI is called, what it is asked to do, what gets decided automatically
vs. left to the human, and the explicit engineering decisions behind each
piece. Sourced from the current codebase (`src/lib/ai.server.ts`,
`src/lib/content-engine/`, `src/routes/api/*`, `src/routes/_authenticated/*`)
and `docs/ENGINEERING_PLAN.md`'s decision log. Nothing here is aspirational —
every capability described is live code on `main` as of this audit.

## Providers in play

| Provider | Used for | Why |
|---|---|---|
| **Anthropic Claude** (`claude-sonnet-4-6`, `ANTHROPIC_TEXT_MODEL` to override) | All text and structured-JSON generation: onboarding research draft, diagnostic report, content plan, carousel outline, video storyboard | Explicit, scoped request from the user ("all the text and all diagnostic work" → Claude), made 2026-09-17. Uses Claude's native structured outputs (`messages.parse` + a Zod schema) — one schema per call site, no hand-maintained JSON Schema + parallel TS type to drift out of sync. |
| **Google Gemini** (`gemini-3.1-flash-image` / "Nano Banana 2"; was `gemini-2.5-flash-image` until its 2026-10-02 shutdown) | All image generation | Not in scope for the Claude move; stayed on Gemini. |
| **Google Veo** (`veo-3.1-generate-preview`) | Short vertical video rendering for Reels/Stories | Async `predictLongRunning` job, polled client-side every 8s. |

Both providers are wrapped in one file, `src/lib/ai.server.ts`, so every
call site goes through the same error handling, retry logic, and API-key
gating rather than each route reimplementing it.

## The user journey, AI touchpoint by touchpoint

### 1. Sign-up (`/auth`) — no AI
Email/password only (Google OAuth was dropped in the Lovable-exit pass).
Nothing to automate here.

### 2. Company registration (`/painel`, first visit) — AI kicked off in the background
The user fills in name, segment, employee count, and optionally
website/Instagram/LinkedIn. The moment that form is submitted, **if any
website or social handle was given, the app fires `/api/pesquisa-empresa`
in the background** without waiting for the user to ask — a decision to
save a step, not a click the user takes themselves. Failure is silent
(best-effort): the diagnostic page also offers a manual retry, so a failed
background call never blocks the user.

### 3. `/api/pesquisa-empresa` — AI research draft (automated, background)
**What it does:** asks Claude to draft plausible answers for the upcoming
diagnostic questionnaire (audience, market/competition, differentiators,
likely goals) from nothing but the company name/segment/handles typed at
signup.

**Explicit, load-bearing decision:** this endpoint does **not** fetch the
given URL or social profile. The model is told point-blank it has no
internet access and must reason from general market knowledge only, must
mark low-confidence fields as `confianca: "baixa"`, and must never invent
specific facts (numbers, awards, real reviews) as if confirmed. Actually
fetching the site for grounding is a known, deliberately deferred follow-up
— it needs an SSRF-hardened fetcher (private-IP/DNS-rebinding guards,
redirect limits, size caps) first, and the team explicitly declined to
build that fetcher just to skip the hardening for this one call site.

**What's automated:** the draft is written straight to `companies.research`
with no human step in between. **What's left to the human:** the diagnostic
form shows these as editable, labeled suggestions the user corrects, not
final answers — and the one field AI is structurally unable to infer
(segment-specific ethical/regulatory restrictions, e.g. CFM for clinics,
OAB for law firms) is left blank for the human to fill.

Quota: `pesquisa_empresa` — 15/day, 60/month per company.

### 4. `/diagnostico` — AI diagnostic report + auto-seeded missions
The user answers the (AI-pre-filled) questionnaire. `/api/diagnostico`
sends it to Claude with a system prompt that:
- Fixes the persona (senior digital-marketing consultant for Brazilian
  SMEs/clinics), language (pt-BR, plain, actionable), and hard limits (max
  5 items per list, 220 chars each, 5–7 missions, XP 50–200, score 0–100).
- **Bakes in a compliance guardrail directly into the prompt:** "respect
  segment-specific ethical/regulatory restrictions (CFM for clinics, OAB
  for law firms) and never suggest outcome guarantees" — this is enforced
  by instruction, not by a separate filter, and is fed the "restrictions"
  field the user (or, upstream, the AI draft) supplied.

**What's automated, no human step:**
- The report (summary, strengths, opportunities, recommendations, content
  pillars, 0–100 score) is saved to `diagnostics` immediately.
- **Missions are auto-generated by the same call and auto-seeded** into the
  `missions` table (up to 8, XP clamped 10–300) — the human never writes or
  approves individual missions, only completes them later. This only
  happens once per company (checked via `existing?.length`), so re-running
  the diagnostic doesn't duplicate the mission list.
- Score is clamped server-side (`Math.max(0, Math.min(100, ...))`) — the
  model's raw output is never trusted as already in range.

Quota: `diagnostico` — 10/day, 20/month.

### 5. `/trilha` — gamified missions (no AI call here, but AI-originated content)
Every mission on this screen was written by the AI in step 4. Completing
one calls `complete_mission` as an **atomic database RPC**, not a
client-side XP read-modify-write — a deliberate fix for a real bug class
(two missions completed in quick succession could lose XP, and a
client-side update let any signed-in user set their own XP by hitting the
table directly). Completing the *first* mission auto-advances the
onboarding stepper (`onboarding_step: "missions" → "content"`) — one-way
only, never overwrites a later step a user has already reached.

### 6. `/marca` — brand identity (no AI; this is what AI reads back later)
Fully manual: logo upload, one of three fixed palette options, a font
pairing, a tone-of-voice choice. No generation happens here — but every
choice made on this screen becomes an input to every downstream image and
text prompt via `buildStyleAnchor()` (see step 8). Saving this form is what
auto-advances onboarding to `"missions"`.

### 7. `/api/plano` — AI monthly content calendar
Generates up to 12 scheduled posts (day, channel, format, pillar, title,
caption, hashtags, CTA) for the coming month, grounded in the brand kit's
tone and the diagnostic's pillars/summary. Requires a brand kit to exist
first (409 if not) — the plan literally cannot be generated before the
brand identity step.

**Decisions:**
- **Idempotent by design:** re-clicking "generate this month's plan"
  **replaces** that month's plan (upsert + delete-then-insert) instead of
  duplicating it — explicitly called out as a fix for a real prior bug
  where re-running produced ever-growing duplicate rows.
- The prompt hard-bans outcome promises in health-adjacent content
  ("Nada de promessas de resultado em saúde") — the same compliance
  posture as the diagnostic, applied here independently since this is a
  separate model call.
- An empty AI response (`publicacoes.length === 0`) is treated as a hard
  failure (502), not silently accepted as "plan generated, zero items."

Quota: `plano` — 10/day, 10/month.

### 8. `/conteudo` → `/api/arte` — AI asset generation (image / carousel / video)
For each planned content item, the user triggers generation. One endpoint,
three branches by format:

- **`post`/`stories`/`artigo`** → `generateStaticArt()`: one Gemini image.
- **`carrossel`** → `generateCarousel()`: Claude first writes a 4–6 slide
  outline (cover → body → CTA), then each slide is rendered as a separate
  Gemini image call, generated **sequentially, not in parallel** — "gentle
  on the gateway," and the quota was already charged once for the whole
  carousel, not once per slide.
- **`reels`** → `generateVideoStoryboard()` (Claude writes a script/shot
  list, 2–6 ~10s blocks) then `startVideoRender()` (Veo, async).

**The style anchor — a cross-format consistency decision:** every image and
video prompt in this pipeline is prefixed with `buildStyleAnchor()`, a
plain-text description of the company's palette, tone, and segment (pulled
from `/marca`). This is explicitly documented as generalizing two patterns
already proven elsewhere in the org (AgrosTech's brand-anchored carousel
pipeline; the Higgsfield/Nano-Banana persistent-reference workflow) into a
brand-kit-driven version any SME's data can drive — with the caveat that
Gemini here only takes a text prompt, not a reference image, so the anchor
is "the text-prompt equivalent of a reference image — same role, weaker
guarantee." If a reference-image-capable provider is added later, this is
the seam to swap.

**The video seam — a decision explicitly *not* made unilaterally:**
`renderVideo` was originally a deliberate stub (`awaiting_provider`) so
that a missing video provider never lost the generated storyboard; wiring
in a real provider (API key, cost) was flagged as the user's call, not
something to fabricate. It has since been resolved for real: Veo is wired
in (`startVideoRender`/`checkVideoRender`), but every "Gerar roteiro +
vídeo" click now spends real money, capped by quota but not otherwise —
the per-call cost is explicitly the user's to monitor, not something the
system throttles beyond the daily/monthly caps.

**Cost control, uniform across all three branches:** `checkAiQuota()` is
called once per request regardless of how many images a format produces
internally — a 6-slide carousel costs one quota unit, not six. Video is the
one exception with *two* separate units: `video_storyboard` (the script,
cheap) and `video_render` (the actual Veo job, "materially more expensive,"
metered separately) — so a storyboard can still be generated and saved even
if the render quota is exhausted.

Quotas: `arte` 20/day·150/mo, `carrossel` 20/day·60/mo, `video_storyboard`
10/day·60/mo, `video_render` 5/day·20/mo (the tightest cap in the app,
reflecting real dollar cost per call).

**Where the media lives:** generated images/video are uploaded to a
private Supabase bucket; only the **storage path** is persisted, never a
long-lived signed URL. The client re-signs a fresh 1-hour URL on render
(`useSignedUrl`/`useCarouselUrls`, `useVideoPolling` polling every 8s for
in-progress Veo jobs) — a deliberate closing of a real gap where an
earlier version saved a 1-year signed URL straight into the row (couldn't
be revoked, silently broke a year later).

### 9. `/redes` (Instagram/LinkedIn publishing) — deliberately deferred
OAuth connection + actual publishing, and the metrics-collection job that
depends on it, were explicitly scoped out this round. No AI runs here
today; this is a known gap, not an oversight.

### 10. `/metricas` — deferred (depends on step 9)
Same reasoning: no publishing yet, so nothing to measure yet.

### 11. `/conta` — data export (LGPD), no AI
One-click export of every row tied to the company as JSON — a compliance
feature, not an AI one.

### 12. `/admin` — read-only oversight, no AI generation, but AI *visibility*
Nav-gated on the `admin` role. Shows every company, its owner, latest
diagnostic score, **and its AI call count** — i.e. the one place in the
product where AI usage becomes visible and auditable by a human, reusing
existing RLS (`owns_company`/`has_role`) rather than a service-role
bypass.

## Cross-cutting decisions worth flagging on their own

- **Fail-closed quota checks.** If the quota RPC itself errors, the app
  treats that as "not allowed" rather than falling through to calling the
  (paid) model anyway — a cost-safety default, not just an error path.
- **No upstream error leakage.** Every AI call site catches provider errors
  and returns a short, generic, Portuguese `userMessage`; the actual
  exception is logged server-side only. This was a named fix — the old
  Lovable-gateway version relayed raw upstream errors to the client.
- **Schema-validated outputs everywhere.** Every text generation call
  passes a Zod schema and gets back an already-validated, already-typed
  result (`z.infer`) — no manual `Array.isArray` defensive checks after the
  fact, no parallel hand-written JSON Schema to drift from a TS type.
- **Compliance language is duplicated per prompt, not centralized.** The
  "no outcome promises," "respect CFM/OAB" instructions live inside each
  system prompt (diagnostic, plan) independently rather than in one shared
  guardrail module — worth noting as a maintenance point: a future
  regulatory update needs to be applied at every call site that generates
  client-facing claims.
- **Everything AI writes is provisional until a human acts on it**, with
  one exception: mission auto-seeding after the diagnostic, which lands
  directly in the gamified trilha with no review step. Every other AI
  output (research draft, diagnostic report, content plan, generated art)
  is either explicitly framed as editable/reviewable or requires a
  separate human click to generate/publish.
